Test a reviewer-verified proposal changelog, using the spreadsheet and original city PDFs. Put document comparison before transcript search: captions missed 7 of 30 sampled amendments because they occurred in written attachments. [F] The neighboring team's linked before/after excerpts and recorded disagreements provide a useful design precedent, not proof of time savings or originality. [I]

For each proposal, assign a local tracking ID and link agenda versions, adopted attachments and votes. Record meeting date, source URL, downloaded filename and a content hash; reused names and changing agenda numbers cannot safely identify a proposal. [G] Reviewers first confirm that two documents concern the same proposal, then compare page excerpts and log the claimed change, evidence and disagreement. An optional free local text extractor or OCR can suggest passages; uncertain matches remain unresolved rather than becoming asserted changes. Votes and amendments should remain separate fields so a vote is not mistaken for proof of exact text.

The hardest assumption is that volunteers can correctly connect proposal versions and identify meaningful changes within two person-hours weekly. [G, H] Start with one proposal across two meetings, including an attachment-only amendment. Each reviewer independently spends at most an hour tracing the documents and identifying changes, then reconcile their logs. Stop or redesign if they cannot establish the version chain, miss the known attachment change, or exhaust the time budget. A passing test only justifies a larger sample. Keep transcript search as a secondary navigation aid. No paid API, subscription or labeled training set is needed for this first test. [F, H]

# Case 4

Start with **local Zotero plus OCRmyPDF**, and pilot **Paperless-ngx's automated intake** as the alternative. This is a provisional choice for a small team without a designated server operator. Actual laptop operating systems and document volume remain unknown.

The conventional route saves web articles through Zotero Connector as metadata plus offline HTML snapshots, and stores scanned PDFs as attachments. OCRmyPDF adds a searchable text layer to a separate scan copy using the local Tesseract engine. Zotero indexes embedded text in PDFs and HTML; an image-only PDF needs OCR first. Check indexing limits: the documented defaults cover 100 pages and 500,000 characters, so a long document can be partly indexed. [Zotero attachments](https://www.zotero.org/support/attaching_files), [searching](https://www.zotero.org/support/searching), [OCRmyPDF introduction](https://ocrmypdf.readthedocs.io/en/latest/introduction.html).

Keep cloud sync disabled for this local pilot; no paid storage or API is required. The operating work is capturing articles, running OCR, attaching the derivative and correcting metadata. This route keeps article provenance close to the readable snapshot. It does not by itself solve team synchronization.

Paperless-ngx changes the mechanism to a watched intake folder: documents are parsed, OCRed, indexed and automatically matched to tags and types. It retains originals alongside archival derivatives, but removes consumed files from the intake directory. Always feed it copies. That integration could remove repeated OCR/import/classification steps, although guessed metadata still needs checking. Its recommended Docker deployment adds a local service stack and maintenance. Web articles would need captured PDF derivatives for this pilot; preserve their HTML snapshots separately because printing can omit content. [Paperless usage](https://docs.paperless-ngx.com/usage/), [setup](https://docs.paperless-ngx.com/setup/). Use a free local container runtime if supported; verify eligibility and compatibility rather than assuming a paid desktop product is necessary.

For either route, preserve untouched downloaded PDFs, all separately downloaded attachments, HTML captures with their resources, source and final URLs, article title/author/publisher, publication date separately from capture time, local ID and cryptographic hash. Keep OCR output explicitly marked as a derivative, with tool/version, processing date, language and review status. These are proposed preservation requirements, not guarantees of automatic metadata transfer. OCR may misread poor scans and columns; PDF/A conversion can change metadata or active content, so a derivative cannot replace the original. [OCRmyPDF limitations](https://ocrmypdf.readthedocs.io/en/latest/introduction.html).

Pilot both on the same 30 documents: ten web articles, ten clear scans, ten difficult scans, including a long document and repeated filenames. Before ingestion, record hashes, metadata and 20 answerable search questions with page evidence. Measure active operator minutes, missed results, incorrect matches, disk use and laptop responsiveness, including cold offline restart. Export and restore into a separate test library; verify every original hash and provenance field. Paperless documents an exporter, but cross-version import is restricted. [Administration](https://docs.paperless-ngx.com/administration/).

Predeclare a decision rule: choose Paperless only if it reduces active work by at least 25%, loses no originals or required metadata, and retrieves at least as many expected answers without making the laptop impractical. Otherwise retain Zotero and automate only the repetitive OCR step. These are pilot thresholds, not measured results.
